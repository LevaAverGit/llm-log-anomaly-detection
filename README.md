# llm-log-anomaly-detection

Compare rule-based and LLM-based incident detection on one honestly-labeled log
corpus, and measure exactly where each approach wins and loses.

## Results

Scored on the same 231 analysis units (22 incidents, 9.5% — a realistic
minority; see [`corpus/README.md`](corpus/README.md)). The rules baseline is
deterministic and is computed directly. The LLM and hybrid rows come from one
local run of gemma3 (via Ollama) whose responses are committed to
`corpus/llm_cache/`, so `make run` reproduces the exact numbers offline;
`make run-llm` recomputes them against the model.

## Run it

```bash
make install                 # create .venv and install dependencies
make run                     # reproduce every row whose response cache is present, offline (rules always; LLM/hybrid once make run-llm has committed their cache)
make run-llm                 # run the LLM detector live against a local Ollama model (needs: ollama pull gemma3:latest)
```

## What I learned

- The rules baseline is high-precision but leaky: on this corpus it scores
  P=0.95, R=0.82, F1=0.88 with a single false positive (4.3 per 1000 units), and
  every incident it does flag gets the ATT&CK technique right (18/18). A Sigma
  baseline earns its reputation for few false alarms, but it pays for that in
  recall.
- The single false positive is not random noise — it is the one boundary case
  the corpus plants on purpose: a high volume of 404s from an ordinary browser
  on sequential paths (a broken-link crawl), which a pure count-based 404 rule
  over-fires on. So the rules' precision cost is concentrated exactly where a
  threshold has no way to see intent.
- The four remaining misses fall into two families the current rule set does not
  cover. One is context that no rule chains: a successful SSH login right after a
  brute-force burst → T1078. (The engine's two correlation rules *do* chain the
  Windows account-creation-after-failures and the cloud IAM-change-after-failures
  cases, so both of those are caught — but nothing links a *successful login*
  back to the burst that preceded it.) The other family is event types with no
  matching rule at all: a standalone Windows 4625 failed-logon burst → T1110.001
  (only the account-creation correlation ever reads 4625, never the burst on its
  own), and host-process semantics — an encoded PowerShell command line →
  T1059.001 and `certutil` fetching a remote binary → T1105. This is the
  hypothesis the LLM arm is meant to test: that a model reads intent where a
  threshold or a missing rule cannot.
- **The LLM recovers the misses — but at a false-positive rate that makes it
  unusable as a standalone detector.** gemma3 with prompt v3 reaches recall 1.00:
  it catches all 22 incidents, including the four the rules miss (the
  post-brute-force login, the standalone 4625 burst, the encoded PowerShell, the
  `certutil` fetch). It pays for that with precision 0.16 and **515 false
  positives per 1000 units** — it flags roughly half of all benign traffic
  (routine logins, ordinary page requests) as incidents. v1 is less trigger-happy
  (P=0.24, 277 FP/1000) but still far past what an analyst could triage.
- **Pushing recall through the prompt just moves the operating point toward
  "flag everything."** v3 (stricter incident definition + ATT&CK context) lifted
  recall from 0.91 to 1.00 over v1 — and dropped precision from 0.24 to 0.16. The
  prompt did not make the model *discriminate* better; it made it *alarm* more.
- **The naive union hybrid is worse, not better.** `rules ∪ LLM` inherits every
  LLM false positive, so it lands identical to the LLM alone (P=0.16, 515
  FP/1000) — strictly worse than the rules on precision, for no recall the LLM
  did not already provide. Union is the wrong combiner. The result points at the
  opposite design: use the LLM as a *targeted second opinion on rule-negative,
  ambiguous units* (triage/enrichment), never as a blanket detector.
- **Negative result, stated plainly:** on this corpus a general-purpose local LLM
  dropped on raw log lines does not beat a Sigma baseline for detection — it
  trades the rules' 18% missed recall for a ~50% false-alarm rate, a trade no SOC
  would take. The honest headline is that the LLM's value here is in triage, not
  in replacing rules.

## Why this is commercially valuable

Every SOC runs on rule-based detection, and every SOC leaks recall through the
gaps between its rules — the correlations and host-process semantics no one has
written a signature for yet. *"Should we add an LLM to catch what the rules
miss?"* is a live, budgeted question on detection-engineering roadmaps, and it is
expensive to get wrong: a detector that doubles alert volume costs analyst hours,
not just compute.

This project is the measurement that answers it before a team commits:

- **It turns an architecture decision into numbers.** The rules-vs-LLM-vs-hybrid
  table — precision, recall, false-positives-per-1000 on one labeled corpus — is
  the evidence a detection lead needs to justify (or kill) an LLM in the pipeline,
  instead of buying the hype.
- **It quantifies the alert-fatigue cost**, the metric SOC economics turn on: this
  run shows the LLM recovering the missed incidents but at a ~50% false-alarm
  rate, and a naive hybrid inheriting that noise — a finding that saves a team
  from shipping an unusable detector.
- **It is reproducible and offline**, so the result can be re-run on a team's own
  logs and model with one command — the difference between a blog opinion and a
  decision a security org can stand behind.
- **It maps to paid work**: detection engineering, SOC tooling, and the emerging
  "LLMs in the security pipeline" evaluation work that AI-security and pre-sales
  roles are scoping now.

In short, it converts *"should we use an LLM here?"* into a measured, defensible
answer — the deliverable a business pays a detection engineer to produce.

## Limitations

- The labels encode one specific criterion (documented in
  [`corpus/README.md`](corpus/README.md)); a different analyst could draw some
  boundary cases differently.
- On the signature classes (web exploitation, scanner recon, cloud
  security-group opening) a unit is labeled from the same objective artifact the
  rule matches — the payload string, the scanner User-Agent, the sensitive port
  — so the rules cannot lose there by construction. The meaningful rules-vs-LLM
  comparison is on the count / correlation / host-process-semantics classes,
  which is where the misses actually are (see
  [`corpus/README.md`](corpus/README.md)).
- The corpus is small and partly synthetic background traffic, so the numbers
  are illustrative, not an industrial benchmark. Its 9.5% incident base rate is
  already a minority but is far higher than a real SOC feed (typically <1%),
  partly because attack bursts are aggregated into single incident units while
  benign traffic is largely one-unit-per-event. False-positives-per-1000 scales
  with prevalence, so the headline 4.3/1000 is optimistic relative to production.
- LLM output is not fully deterministic even at temperature 0, so the headline
  table is read from a committed cache; run-to-run variance is reported
  separately.
- Runs use a local 7–8B model via Ollama; a larger or cloud model may score
  differently.
